# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Five portable, Claude-style skills for agentic CLIs (Claude Code, GitHub Copilot CLI, OpenAI Codex, Gemini CLI):

- **`adapty-integration`** — guides an agent through integrating the Adapty SDK into a mobile app end-to-end: dashboard setup via the Adapty CLI, SDK install, paywall, store configuration.
- **`ads-manager`** — operates Apple Search Ads through the Adapty CLI's `adapty asa` topic: reading performance, changing bids and budgets, keyword work, launching and pausing campaigns.
- **`flow-audit`** — answers one question, is this Flow Builder flow ready for production, by cross-referencing its config against the live dashboard (catalog, access levels) and returning a verdict plus ranked, fixable findings. Read-only: never writes to a flow. Complements `flow-generator` (which owns writes) and `paywall-teardown` (which owns conversion advice).
- **`flow-generator`** — reads a flow's Flow Builder config (JSON) through the CLI's `flows` topic, transforms it, and writes it back. Touches no app code; touches the CLI for the config itself and for products.
- **`paywall-teardown`** — reads a paywall (a screenshot, a `flows config preview` render, or a flow config) against a pattern library and returns ranked, testable conversion hypotheses with expected-impact ranges. Touches nothing: no CLI, no files, no network. The growth half of the pair whose engineering half is `flow-generator`.

One repo, three distribution channels: a Claude Code plugin (`.claude-plugin/` holds the marketplace + plugin manifests), the skills.sh CLI, and plain directory copy of a `skills/<name>/` directory into a tool's skills folder. Keep every skill directory self-contained and format-portable — nothing in one may assume Claude Code specifically.

All five skills ship inside the single `adapty-skills` plugin, because a plugin exposes every skill under `skills/`. No manifest edit is needed to add one. The plugin name is deliberately broader than any one skill — installing it gives you every skill in the repo, and that is the intended shape. Splitting the skills into separate marketplace entries was considered and rejected; do not reopen it without a reason the plugin name no longer covers.

`marketplace.json` also carries a **deprecated `adapty-sdk-integration` entry** pointing at the same `source: "./"`, so installs made under the old plugin name keep resolving and keep updating. Verified: `plugin details` through either handle reports the same plugin identity and the same skill inventory. Drop that entry only after the docs stop teaching the old handle — never before, or you break the installs it exists to protect.

**Three namespaces, renamed together:** the GitHub repo is `adapty-skills`, the plugin is `adapty-skills`, and the SDK skill is `adapty-integration` (the ads and flow skills keep their names). They are independent namespaces that happen to agree now — a future change to one does not imply the others. Note the repo rename has no alias mechanism the way the plugin does: GitHub redirects git and web traffic from the old name indefinitely, but **`raw.githubusercontent.com` does not follow renames**, so any consumer fetching raw file URLs breaks the moment the rename lands and must be updated in the same wave. The redirect also dies permanently if anything is ever created at `adaptyteam/adapty-sdk-integration-skill` again, so never reuse that name.

## Layout

- `skills/adapty-integration/SKILL.md` — the skill entry point. Phase-by-phase flow: state tracking → setup (docs-fetching rules, session marker, feedback consent) → project analysis → three user questions → dashboard setup through the Adapty CLI → staged, per-platform implementation → closing review → feedback delivery. Platform-agnostic on purpose; per-platform details belong in references.
- `skills/adapty-integration/references/<platform>.md` — one per platform (`ios`, `android`, `flutter`, `react-native`, `unity`, `kmp`, `capacitor`) plus `testing-setup-{ios,android}.md`. Code snippets and the exact docs URLs the agent fetches before writing each piece of code.
- `skills/adapty-integration/references/migration.md` — the cross-platform migration spine: source detection, mapping rules from another purchase system's concepts to Adapty's, and the `ADAPTY_SETUP.md` handoff contract. Injected on every run where `migrationSource` is set, alongside the platform reference; kept lean on purpose, since a headless run can't skip past padding. `references/migration-<source>.md` (currently `migration-revenuecat.md`) adds source-specific mapping and is also cross-platform. Two files are the odd ones out, loaded **on demand only** and never injected by default: `references/migration-architecture.md`, when a call site has no one-to-one Adapty equivalent, and `references/migration-flow-rebuild.md`, when `paywallApproach` is `flow_builder` and the app renders its paywall screen itself — the one migration that retires the app's own UI instead of rewiring it. That file owns the two rules the spine can't state generally: no CLI-created placements on such a run (the flow needs those developer IDs), and the screen's copy, assets, and locales get extracted into the handoff before any code changes, because the user rebuilds it in a visual editor from what the agent wrote down.
- `skills/ads-manager/SKILL.md` — the ads skill's entry point. Ten named workflows (orient, report, launch, harvest keywords, optimization pass, pause/resume, custom product page, diagnose a dead ad, automations, competitor check), a money-safety contract in prohibition + rationalization-table + red-flags form, the shared account surface, the one-question-one-call rule, and the fallback chain. Drives the `adapty asa` topic, added by [adapty-cli#8](https://github.com/adaptyteam/adapty-cli/pull/8) and shipped in `adapty` 0.4.0.
- `skills/ads-manager/references/asa-management.md` and `asa-metrics.md` — the writing half and the reading half. Management owns per-entity create/update flags, the scope-filter matrix, batch caps, idempotency and the catalog/write budgets; metrics owns entity levels, cohort windows, date-window caps, the metric vocabulary and the analytics pool. The split is load-bearing: the two halves share almost no vocabulary, so a "how did last week go" request loads one file and "add these keywords" the other. `SKILL.md` links into both by exact heading string — `## Scope filters`, `## Writes and idempotency`, `## Status`, `## Cohort windows`, `## The analytics pool` — so renaming a heading breaks the entry point silently.
- `skills/flow-audit/SKILL.md` — the audit skill's entry point. Five phases (resolve/authenticate → select the flow → fetch config + catalog → run `verify-config.py`, `audit-flow.py --report`, `flows config validate`, in that order → report), read-only throughout, and a verdict rule that never certifies what it could not see: `READY FOR PRODUCTION` only when zero blockers fired **and** every open `question` has been put to the user, otherwise `READY, PENDING n CHECKS I CANNOT MAKE`. The report ends in two fixed closing elements — `BEFORE YOU SHIP` (unverifiable-by-design reminders, chiefly the placement link) and, whenever at least one finding fired, a **`WHAT TO DO NEXT`** section that routes every numbered finding into one of four groups by check name (`Answer these` for a verdict-conditional question, `Change in the flow`, `Change in the Adapty dashboard`, `Optional` for a risk) — every finding number is guaranteed to appear there, never silently dropped from the plan.
- `skills/flow-audit/references/audit-flow.py` — the six-family completeness checker (stdlib only): triggers, store compliance, products, variables, localization, placeholders. Takes the bare config plus the catalog JSON; `--report` prints the user-facing block (verdict, findings, locale coverage, `BEFORE YOU SHIP`, `WHAT TO DO NEXT`), `--json` prints raw findings, no flag prints a plain list. Exit 0 no blockers, 1 at least one blocker, 2 usage/unreadable input.
- `skills/flow-audit/references/checks.md` — per-check evidence: what each check looks at, its severity and why, its calibration result against the tracked fixture corpus and real flows, and the false-positive/false-negative trap it closed. Read before changing a check.
- `skills/flow-generator/SKILL.md` — the flow skill's entry point. Owns the **five-phase workflow** (authenticate → decide new-vs-existing flow and transform → `flows config validate` → `flows config preview` + screenshot + iterate → `flows config update`, read back, hand off the publish), the safety contract (`--expected-updated-at` on every write but the first, never write to a flow the user did not name, prefer a fresh `flows create` for new work, no `flows delete` so never claim to have deleted one), and the verify checklist. The phase ordering is load-bearing: validate and preview both run on a **local file**, so the loop converges before anything is written — one write instead of one per iteration. Four transforms are in scope and a request outside them is named as out of scope, not improvised: add a locale, rewrite copy, add/remove/reorder screens, branching and conditions. Transforming a real config is the default and the safer path, but **authoring is in scope too** and the skill ships `references/flowkit.py` for it. Exactly three things cannot be synthesized: **`flowProductId`** (builder-only; measured not to be a plain UUIDv5 over the obvious inputs), **an asset nobody has a file for** (given a file, `flows media upload` places it — SVG and video excepted), and **real store prices**. The earlier, broader claim — that product UUIDs, icon SVG and the `theme` were also unsynthesizable — was disproved by building several flows from screenshots; do not restore it, because an agent that believes it refuses work it can do.
- `skills/flow-generator/references/flow-schema.md` and `transforms.md` — the shapes half and the risk half. `flow-schema.md` owns the envelope, the browser-export-versus-CLI-config distinction, the element/action/sizing vocabulary (recorded with per-file provenance, and explicitly a floor rather than a closed set), the shape traps, and the invariant table. `transforms.md` owns, per transform, which invariant is at stake, which publish blocker it trips, and what has to be disclosed to the user. The split is load-bearing the same way `ads-manager`'s is — a copy rewrite needs the rich-text rules and nothing about branching; a quiz rewire needs the condition wiring and nothing about locales. `SKILL.md` links into `transforms.md` by exact heading string, so renaming a heading breaks the entry point silently.
- `skills/flow-generator/references/preview.md` — the evidence behind phase 4, split out to keep the entry point loadable: why the URL is unreadable, what a screenshot is and is not evidence of, the **six render blindnesses**, the four disagreeing surfaces, and the failure path (analytics beacons choke on a large fragment → use the file-input script, never a smaller config). `SKILL.md` phase 4 is now the loop alone and links here by heading.
- `skills/flow-generator/references/validate.md` — the `flows config validate` evidence, split out because a run only needs it when validate says no. Owns the coverage matrix in both directions (what it catches, what it passes), the three message families, the one-fatal-per-run mechanic and the two call traps (bare config not envelope; the flow must exist). `SKILL.md` phase 3 holds the commands and the exit condition and links here.
- `skills/flow-generator/references/media.md` — the asset path, split out because a copy, locale or branching run never needs any of it. Owns `flows media upload`'s call shape and the `sed`-off-stdout URL capture (never `--json`, which inlines a base64 thumbnail), the accepted-format and byte-cap measurements, the two shapes an uploaded URL binds into (per-locale `values` map on an `image` element versus flat inside a `fill`), the string-`id` rule, the measured geometry table for `hug`/`fixed`×`cover`/`fit`, and the finding that makes the phase ordering load-bearing: neither publish-time gate looks at an image, and a placeholder does not occupy the space the real asset will. `SKILL.md` links into it by exact heading string, so renaming a heading breaks the entry point silently.
- `skills/flow-generator/references/products.md` — product binding, split out because a locale or copy run never needs any of it. Owns the fact that a flow's `product.id` and the Adapty product UUID from `adapty products list` are the same namespace (verified, not inferred), the read-only lookup chain (`apps list` → `access-levels list` → `products list`/`get`), the `products create` write and its confirmation gate, and the `--period`-versus-price-variable agreement check. It also records the three ways `products create --help` misdescribes required flags (all found by running the command, not by reading it) and the fact that a `const` purchase action binds a product with no `product` element — while the flow stays **unpublishable** until that product is declared in `_meta.screens` anyway (corrected 2026-08-24; see the validate bullet).
- `skills/paywall-teardown/SKILL.md` — the paywall skill's entry point. Owns the **two directions** — audit a paywall someone else will change, or *design*, which is entered on an observable predicate (**no design reference was given**: no reference image, no screen to copy, no layout spec) and runs two passes, the second of which grades and corrects the agent's own render — the three input forms (screenshot / `flows config preview` render / flow config), the internal four-step process, the two output formats, the verbatim disclaimer, the conditional CTA, and the framing rules that keep the numbers honest. Adapted from Adapty's growth-team `paywall-teardown` skill shipped on claude.ai; the additions here are the render/config inputs, the design-brief direction, the `## What you cannot invent` section, and the two-way link with `flow-generator`.
- `skills/paywall-teardown/references/patterns.md` — the pattern library: 15 patterns plus category playbooks, each with when it applies, its cross-check, its impact tier and its category-level grounding. **Kept at that filename deliberately**, matching the upstream skill so a growth-team update to the library copies in as a one-file diff — even though `skills/flow-generator/references/patterns.md` is a different file about layout composites. They never own the same fact: conversion patterns and impact numbers here, JSON skeletons there.
- `tests/` — the fixture corpus for `flow-generator`, plus the repo-only Python helpers that operate on it — sanitizing, rendering, measuring and `test-flowkit.py` (see the `flow-generator` conventions below). Not a test suite for the skills. **`verify-config.py` used to live here as `verify-fixture.py` and moved to `skills/flow-generator/references/` on 2026-08-25 so that it ships, and was renamed at the same time because a runtime agent runs it on its own config, not on a fixture. Every mention of `verify-fixture.py` in the dated findings below was rewritten to the new name: the rounds themselves ran against the old one** — anything in `tests/` is repo-only by definition, so a check an agent must run at runtime does not belong here.
- `scripts/` — the two validation lints and their plain-text allowlists (see below).
- `feedback-endpoint/` — a single Vercel serverless function that receives the end-of-run feedback payload and forwards it to Slack + Airtable. Deployed separately (`npx vercel deploy --prod` from inside that directory); its README documents the env vars and the stable production URL that SKILL.md points at. Has its own tests: `node --test test/endpoint.test.js` from inside that directory.
- `context7.json` — Context7 indexing config.

## Validation lints

**The link lint covers ALL of `skills/`; the symbol lint covers `adapty-integration` and guards the rest.** Widened 2026-08-28 — it previously hardcoded `skills/adapty-integration`, so a green run said nothing about four of the five skills that ship, while the runtime agent is told to fetch URLs from all of them. The widening cost 17 unique URLs and found no dead links; coverage is now printed per skill on every run (`adapty-integration 318, ads-manager 1, flow-generator 21, paywall-teardown 1` — `flow-audit` has none, verified, so its absence from that line is coverage rather than a skip). Two extraction rules were needed and both are load-bearing: a URL containing `…` **or** `...` is a documentation placeholder, not a link — the second came from a real 404 on a media URL inside pasted sample output with the hash cut out (`1e5bbbb4-.../hero-600x400.png`), which is elided-example noise rather than a finding.

**The symbol lint was deliberately NOT widened, and that is a measured decision rather than an omission.** It resolves a file's platform from its name (`references/<platform>.md`) and checks against that platform's docs aggregate; the other four skills have no platform and name **zero** SDK symbols (measured across all their `.md`). But "they name none" is an assumption that rots the moment someone adds one, so it is now checked instead of believed: a **scope guard** scans those four for `Adapty[A-Z]…` / `Adapty.<member>` and turns the lint **red** with a pointer to either drop the symbol or widen the lint. The capital `A` is what separates an SDK symbol from the domain (`adapty.io`) and the CLI (`adapty asa`). Negative-tested by injecting `Adapty.getPaywall()` into `flow-audit`.

There is no test suite for the skills themselves — the lints are the verification gates. Run them after any edit to a SKILL.md or a reference:

```bash
node scripts/lint-symbols.mjs [platform ...]   # default: all platforms
node scripts/lint-links.mjs
```

Exit codes for both: `0` clean (warnings allowed), `1` findings, `2` infrastructure error (docs unreachable — fix the network, not the skill).

- **Symbol lint** — every Adapty-branded symbol used in a reference's code contexts (`Adapty.x` / `adapty.x` / `AdaptyUI().x` member calls, `Adapty*` type names, in fenced blocks and inline backticks) must exist in that platform's official docs. Ground truth is the `<platform>-llms-full.txt` docs aggregate plus pages the reference links; the docs are verified against SDK sources by the docs team's release process, so docs presence transitively means the symbol exists in the SDK. A reference's platform comes from its filename (`testing-setup-*` files are pinned to their platform in the script). Two plain-text escape hatches, editable without touching code:
  - `scripts/app-side-allowlist.txt` — wrapper names the references deliberately tell the *user* to create. They look Adapty-branded but are not SDK symbols; add the name here when a reference introduces a new suggested wrapper.
  - `scripts/undocumented-sdk-symbols.txt` — real SDK symbols deliberately absent from the docs. Each entry pins a source-of-truth code URL and is verified against the SDK source instead, so a rename still turns the lint red. Format: `<reference>: <symbol> <source-url>`.
- **Link lint** — every https URL in the skill must work the way an agent fetches it: `adapty.io/docs` pages are checked via their `.md` variant with query/hash stripped, `*-llms*.txt` aggregates as-is. A docs 404/410 is a hard failure (the skill literally instructs fetching that URL); external links (stores, consoles, GitHub) failing are warnings only, as are docs pages missing from `llms.txt` (they work but agents can't discover them).

CI (`.github/workflows/skill-lints.yml`) runs both lints on PRs and pushes to `main` (red blocks merge) and on a daily cron that catches drift with no skill commit involved — docs renames, SDK releases. A scheduled failure files one deduped `skill-drift` GitHub issue; repeats become comments on it.

## Conventions when editing the skills

These apply to `adapty-integration`; the `ads-manager` section below adds its own.

- **Docs URLs are load-bearing.** SKILL.md forbids the runtime agent from guessing slugs — it may only open URLs written in the skill or found in a fetched `llms.txt` index. So every docs URL you add must literally exist (the link lint enforces this); never assemble one from a topic and platform name.
- **The session marker matters.** SKILL.md tells the runtime agent to mint a random `sessionToken` and tag every docs fetch with `?ref=skill-<sessionToken>` (a docs-analytics marker, documented in SKILL.md's "Session marker" section). Don't remove, rename, or add a literal example token to that format — hardcoded example tokens get copied verbatim by agents, which corrupts the analytics.
- **Test runs from this repo are not real integrations.** When you run or debug the skill from inside this repo, have it tag docs fetches with `?ref=skill-dev-<sessionToken>` instead (or drop the `ref` on ad-hoc curl spot-checks), so Adapty's docs analytics can tell development traffic from real usage. The lint scripts already strip refs and need no special handling.
- **New wrapper names need the allowlist.** If a reference introduces a new app-side wrapper (service, notifier, context, constant) with an Adapty-ish name, add it to `scripts/app-side-allowlist.txt` in the same change, or the symbol lint turns red.
- **New platform = new reference + docs coverage.** Add `references/<platform>.md` and confirm the docs publish `<platform>-llms-full.txt` — the symbol lint builds its ground-truth corpus from it.
- **New migration source = new reference + spine row.** Add `references/migration-<source>.md`, add a row to the spine's detection table, and add the source to the CLI's picker if the CLI should offer it. No lint edit is needed — the symbol lint prefix-matches `migration*` and derives the platform list.
- **Migration references are linted against the union corpus.** Their Adapty symbols are still verified, so they may name Adapty APIs; they carry mapping and strategy and delegate platform code to `references/<platform>.md`. Dead `revenuecat.com/docs` links are hard lint failures — take RC URLs from `https://www.revenuecat.com/docs/llms.txt`, never assemble one.

## Conventions when editing `ads-manager`

- **Verify against per-command source, never prose and never flag-set composition.** Ground truth for the `asa` surface is each command's own `static flags` declaration in `adaptyteam/adapty-cli`. The CLI's prose docs contradicted that source in four separate places while this skill was written (`--search` coverage, `--page-size` limits, `--period-unit` casing, `product-pages sync` 200 semantics), and composition misleads in its own way — `orgScopeFlags` contains no `--org`, which is exactly where a hallucinated `--org` list filter came from. Read `src/commands/asa/<topic>/<command>.ts`, not the tables.
- **The surface moves.** This skill was authored against adapty-cli#8 while it was open, and that branch gained a commit mid-authoring which silently invalidated facts already verified — `--page-size` limits, the request budgets, the 429 retry behaviour. It merged at `47528602`, the commit the current content is verified against. Pin the commit you verify against in your notes and re-check numbers rather than trusting a previous pass, because the next CLI release will do this again.
- **The safety content is evidence-backed, not authored.** The rationalization table carries exactly two rows, both byte-exact quotes from agents in `docs/superpowers/baselines/2026-08-11-asa-baseline.md`. Never add a row without a real quote from a real run — a fabricated excuse teaches a failure mode nobody exhibited. Red flags are grouped by provenance: those observed in this skill's own baseline, and those adopted from CLI-side reports. Keep the groups separate so a reader can tell which armor rests on measurement.
- **Match the form to the failure.** Two rules had to be rewritten because the form was wrong, not the content. A rule that governs intent ("never pass `--yes` until the user agrees") is satisfiable by an agent that plans to comply while the command on the page already carries the flag — ground it in an observable mechanism instead (`--yes` deletes the preview the CLI would print). And a rule with no compliant use will get an exception invented for it: the same `--yes` prohibition forbade the flag unconditionally in every realistic request, so it became two conditionals keyed to who runs the command.
- **Slots beat reminders.** Required elements live in the command templates as slots an agent cannot fill from memory — `--idempotency-key <key>`, and the deliberately clumsy `--<filter-from-that-list-s-matrix-row>`. That token's length is load-bearing: shortening it back to `--<scope-filter>` makes it fillable by guessing and reopens a closed hole.
- **Changes get pressure-tested, and one clean sample proves nothing.** The scenarios and the twelve-row checklist are in the baseline document. A clean round was twice shown to be luck by re-sampling the identical skill, so a rule is considered closed only after two consecutive clean rounds.
- SKILL.md and the references are agent-facing prose: imperative, unambiguous, no dead weight. Match the existing voice and structure when editing.

## Conventions when editing `flow-generator`

Every rule below exists because it was violated while the skill was built.

- **One owner per fact; link, never restate.** `references/products.md` owns product binding, `references/flow-schema.md` owns shapes and invariants, `references/transforms.md` owns per-transform risk and the five-item disclosure contract, and `SKILL.md` owns workflow, safety, verify and preview. A fact stated in two files will drift, and it did inside a single authoring session: `flowProductId` was described as flow-scoped in one file and assignment-scoped in another, and only one of those is true. When a second file needs a fact, link to the file that owns it.
- **Do not write guidance for a trap the baseline already closed.** Measured against skill-less agents in `docs/superpowers/baselines/2026-08-19-flow-generator-baseline.md`: they preserve rich-text `variable` price nodes (2/2), repair a dangling `navigate` nested in a `conditional`'s `default` branch (2/2), and find all 42 localizable fields (2/2). What actually failed was `status`/`id` on re-upload (0/4) and undisclosed structural decisions — bare-string `content` handling split 2 agents left / 2 converted, with 0/4 disclosing it as a choice. Content that teaches mechanics agents already have is padding, and padding is what a headless run cannot skip past. Guidance earns its place by naming stakes and forcing disclosure, not by walking JSON.
- **`--help` is not the command manifest. Enumerate `dist/commands/`.** `flows config validate` and `flows config preview` exist in the package, are listed in `oclif.manifest.json`, and were **absent from `flows config --help`** on the version checked — which produced a confident, wrong claim that neither command existed. The reliable enumeration is `find "$(npm root -g)/adapty/dist/commands" -name '*.js'` (or the npx cache path), plus reading the command's own `static flags` and `static description`. This is the same rule `ads-manager` already carries, one level deeper: not just "prose lies about flags" but "help output omits whole commands."
- **Check which version you actually invoked.** The 404-on-validate investigation crossed two versions without noticing: `npx adapty@latest` ran **0.6.0** while the inspected npx cache directory held **0.6.1-beta.0**. `validate`/`preview` were in the beta only *at that time* (both are stable now — see the version-floor bullet). Print `--version` in the same command as the thing you are testing, and never read a cached `node_modules` as evidence about a different tag.
- **The `flows` CLI version floor is per command, verified from the published tarballs, and it does not move monotonically.** Read off `npm view adapty@<v> dist.tarball` + `tar -tzf | grep commands/flows` — the only enumeration that neither `--help` (hides commands) nor a global install (usually stale) can lie about. `flows` + `config get/update` from **0.6.0**; `config preview` from 0.6.1-beta.0 and **stable since 0.7.0**; `config validate` in 0.6.1-beta.0, **absent from 0.7.0**, back in 0.8.0-beta.0 and **stable in 0.8.0**; `flows media upload` 0.8.0-beta.0 and 0.8.0. Two consequences the earlier "validate and preview are beta-only" note got wrong: **`@beta` is not needed for the normal loop** (stable `latest` covers phases 1-5, preview included), and **a command can leave stable again**, so "a later version has it" is not inferable from an earlier beta. The skill now resolves **`$ADAPTY`** once in phase 1 — `adapty` if `--version` is >= 0.8.0 (raised from 0.7.0 when `validate` landed in stable), else `npx --yes adapty@latest` — and every runnable example is written against that variable rather than a bare `adapty`, which is what let three agents conclude the commands did not exist. **`--yes` is load-bearing**: without it npx asks permission to install an uncached package and a headless run has nobody to answer. Facts about behaviour, each established by running the commands: `config get` returns an **envelope** (`{config, remote_configs, status, updated_at}`); `--expected-updated-at` wants the **epoch integer** from `config get` and rejects the ISO timestamp `flows create` prints; `validate` is advisory, exits **1 for both "not publishable" and "API error"**, so the `--json` `valid`-versus-`error` distinction is load-bearing (its endpoint 404'd against production through 0.8.0-beta.0 and is **live from 0.8.0** — see the validate bullet below); `preview` is **fully local** (no `--app`, no flow id, no auth) and accepts an envelope or a bare config; `flows media upload` is **live in production from 0.8.0** (see its own bullet); and there is **no publish and no delete**, so both stay dashboard actions. **Never invent a command name or a flag** — if a command is absent, the skill says so and falls back.
- **`flows config validate` shipped in stable `adapty` 0.8.0 with its endpoint LIVE IN PRODUCTION, and it runs the real publish-time transform service — so the skill gained a pre-write publish gate it never had.** Measured 2026-08-24 against production with real flows in `app_finance`; `validate.js` is byte-identical between 0.8.0-beta.0 and 0.8.0, so the change is purely the endpoint going live. What it catches, each by injecting the defect into a previously-clean real config: an undeclared product (`props.product` **and** `.purchase.product`), a `groupId` naming no declared group, a `navigate` (or a screen deletion) stranding a target, a `hierarchy` id with no `map` entry, a `defaultLocale` naming no configured locale, a stray declared locale, a malformed hex. What it passes: `fill: "banana"`, `schemaVersion: 999`, top-level `status`/`id`, a missing `states`, a missing `defaultLocale`, a hyphenated element id (the black-screen class), and **every advisory warning** — a successful run returns `issues: []`, not a warning list, so the silent-success channel stays unreachable from the CLI and the phase-5 device callout stays load-bearing. Three mechanics that shape how the skill uses it, all measured: it is **version-agnostic** (a v9 config validates clean, so no baseline), it takes the **bare config and rejects the envelope** with `Invalid flow input` — which reads exactly like a broken config — and **it reports one fatal per run** (three injected defects → one issue; adding the third changed *which* one came back). Hence phase 3's exit condition is a run that printed `valid: true` over the bytes about to be written, and Verify is walked **first** because it names every defect locally in one pass where validate needs a round trip each. Also measured and worth not overclaiming: a flow sitting in `publication_failed` validates clean, so `valid: true` is "no blocking objection to this document", never "publishing will succeed".

But `tests/fixtures/tabs-paywall.json` is a real builder export at `schemaVersion 9` carrying **15 array fills**, and it renders. So the version rule explains why two forms exist; it does not license converting between them. The operating rule stands: read the input's form and keep it.
- **`old-price` is the strikethrough element, and this project got that wrong first.** It carries no content and no product reference, only a `multiplier`, so it derives a "was" price from the enclosing product. The earlier conclusion — that a price strikethrough needs `offer_price` or an annual/monthly pair — is true only of a `text` element holding a price variable. If a correction like this is ever reverted, check whether the claim is about the *element* or about *one way of faking it with text*.
- **Phase 5 ends with a fixed four-line callout, and it is not optional padding.** Review link (with "refresh if open"), preview in the **Adapty mobile app**, publish via the **top-right button in the editor**, and the closing line that until they publish nobody sees the change. It is written as a fill-in template rather than advice because consistency is the whole value: a saved-but-unpublished config is indistinguishable from a shipped one, and there is no `flows publish` for an agent to reach. Do not trim it for small edits.
- **Four preview surfaces, in increasing fidelity, and they disagree:** `config preview` + screenshot (a different renderer — layout only), the Flow Builder editor (can the authoring tool open it), the **Adapty mobile app** (the real SDK renderer — the only one that would surface the `unsupported_text_typography_setting`-class warnings the transform service reports), and published-and-live. An agent can only reach the first, which is exactly why the callout asks the user for the second and third rather than treating a screenshot as sign-off.
- **Shape and publishability are two separate gates and neither subsumes the other.** `flows config validate` answers *is this publishable* and skips most prop shapes — it accepts `fill: "banana"` and `schemaVersion: 999`. A schema check answers *are the props well-formed* and knows nothing about publishability. `SKILL.md` phase 3 runs both, in that order.
- **A schema check without `--baseline` is noise, and noise trains you to ignore findings.** The schema tracks the newest `schemaVersion` while most live flows are older. Measured on `onboarding-quiz-paywall.json`: 28 errors unbaselined, 0 baselined against itself, and one deliberately broken `width.type` surfaces as exactly one finding. Both the official `validate-with-schema.mjs` and `tests/schema-check.py` take `--baseline`; the baseline is the pristine copy from `get`, which is the other reason step 2 keeps a backup.
- **`skill-validator check` (agent-ecosystem/skill-validator, v1.2.0) ran over both new skills on 2026-08-22; `paywall-teardown` passed clean, and `flow-generator`'s two errors are accepted deviations, not defects.** Both errors are token-size complaints that assume references are read whole: `component-catalog.json` (73K tokens) is queried with `jq` and never read whole by explicit rule, and the reference total counts two executed scripts and an imported module. The real findings it produced: a `__pycache__/` inside `references/` — which the copy-install path would have shipped — now prevented by `sys.dont_write_bytecode` in the tests that import flowkit; and SKILL.md at 7,639 tokens against the spec's < 5,000 recommendation, which stands as the follow-up target for the next evidence-eviction pass (candidates: the Verify list's overlap with flow-schema's invariant table). Its LLM-scoring lane needs `ANTHROPIC_API_KEY` in the shell and has not run. Treat its size errors on the catalog as permanently-accepted: splitting a jq-queried database into readable chunks would optimize the metric and break the access pattern.
- **CI does not cover this directory.** `scripts/lint-links.mjs` builds its target as `join(..., 'skills', 'adapty-integration')`, so every URL under `skills/flow-generator/` is verified **by hand with curl** — no exceptions, since the skill instructs the runtime agent to fetch those URLs. Widening the lints to walk all of `skills/` is an open follow-up that would remove this manual gate for both `flow-generator` and `ads-manager`.
- **Fixtures are sanitized, and the sanitization has a documented blind spot.** `tests/fixtures/` holds a tracked three-export corpus; the raw exports stay gitignored at `tests/fixtures-raw/` because they carry real product UUIDs and real media URLs. `tests/sanitize-fixture.py` regenerates the tracked copies (consistent UUID remapping so every internal reference still agrees, plus placeholder asset URLs) and `skills/flow-generator/references/verify-config.py` checks the referential invariants of a fixture. The limitation to keep recorded: remapping breaks the `flowProductId` UUIDv5 derivation, so a sanitized fixture cannot demonstrate that relationship — verify anything about it against a raw export.
- **`_meta.screens[].products[]` is builder-owned bookkeeping.** Never hand-author it and never copy it between flows. Evidence from a live round-trip: on attachment the builder rewrites `product.id`, regenerates `flowProductId`, and rewrites every price `variableId` that was keyed to the old product id — while element ids survive byte-stable. Price variables therefore self-heal on attachment, which is why a wrong product id is a human-repaired inconvenience and a hand-authored `products[]` block is a lie the builder will overwrite.
- **`patterns.md` carried a retired rule for a whole release, and a live run is what found it.** Its plan-card section said *write the prices as plain text, not price variables* — the pre-declaration rule, superseded by `flowkit.predeclare()` and the measured device preview. Nothing broke, which is why it survived: an agent following it produces a paywall that renders perfectly and ships a **fabricated price**, and the config gives no sign. It surfaced only when `paywall-teardown`'s “what you cannot invent” contract collided with it head-on in a real build. Two rules from that: when a fact is superseded, **grep every reference for the old rule in the same change** — ownership boundaries stop drift between files, not inside one — and prefer the failure that is *visible* (a missing element, a 422) over the one that renders clean.

- **`references/flowkit.py` is shipped skill content, and `tests/test-flowkit.py` is the reason it can be.** It owns the *mechanical* half of authoring — the `hierarchy`/`map` split above all, plus the envelope and one canonical rich-text builder — and deliberately owns nothing with a design opinion, because shapes and spacing are `patterns.md` and those are judgement. It exists because five ad-hoc build scripts in one session redefined the same ~90 lines and drifted: three `runs()` helpers agreed on the name and disagreed on whether a tuple meant a variable node or a coloured span, so a call copied between flows produced the wrong node type silently and still published. Hence named `Span`/`Var` types and a hard `TypeError` on a bare tuple. Two rules when editing it: **a shape helper that has drifted is worse than none**, so never change it without running its test (19 checks, ending in the real schema gate), and **keep design out of it** — the moment it grows card recipes or spacing presets it starts competing with `patterns.md` for the same facts.

- **Binding a product is an agent's job; declaring it is the builder's, and that is a handoff, not a wall.** Measured: a config written with bound `product` elements and `_meta.screens: {}` came back from a later `config get` with the declaration filled in and both `flowProductId`s minted, because the owner opened the flow — **nobody re-picked anything**. An agent still cannot author the declaration (`flowProductId` is a UUIDv5 over an input the config does not contain: 2,944 combinations tested against 5 real triples, no match, and one product on two screens gets two ids). **The agent can declare the products itself, and should, for a flow it authored** — measured: a draft carrying two fabricated `flowProductId`s, never published and never opened in the builder, previewed on a real device cleanly, because the transform service checks that a declaration is present and consistent rather than that the value is the builder's own. `flowkit.predeclare()` generates one; never call it when rewriting a flow, where the live `_meta.screens` must be carried forward. Without a declaration the rule took three passes to get right: the builder declares when it **saves** (an edit, or publishing), not when it opens, so **device preview on a freshly authored flow returns HTTP 422** (`missing_flow_product_id` per product, `unknown_product_id` per price variable) and **publishing fixes it**. Device preview is a stricter gate than `config update` — the write endpoint does not run the transform service and the preview does — so a clean write says nothing about whether the flow previews on a device. Price variables authored before the declaration exists do resolve once it lands (verified: 51/51 element ids and every `variableId` preserved verbatim through publish). An earlier, gloomier version of this said the user must re-pick each product and that authored configs therefore cannot use price variables at all; that overstated it, and `skills/flow-generator/references/verify-config.py` accordingly reports a bound-but-undeclared product as a **warning**, because an agent-authored config is expected to look that way.

- **Product selection is an ordered dialogue — catalog, then store ids, then create — and it happens before the design.** The gap was found in this repo's own live runs: the agent picked catalog products silently, which worked only because the sandbox had one obvious set; on a real account a silent pick decides what the user sells, invisibly to every render check. Order is load-bearing twice: asking for **store product ids** (Google needs product id + base plan id) before reaching `products create` is what keeps the create from stalling on its required bindings, and the catalog gates the archetype choice (verified offer → trial timeline; period-only differences → switcher), so products resolve before `paywall-teardown` briefs the screen.
- **`products create` writes to a live dashboard.** It carries the `ads-manager` safety form rather than a prose reminder: echo the exact resolved flag values, get an explicit yes, then run. Reads — `apps list`, `access-levels list`, `products list`/`get` — need no confirmation and should be used freely.

- **Snippets (`references/snippet.py`, `references/snippets.md`): two corpus measurements, taken across all 10 configs in `tests/fixtures/` and `tests/fixtures-raw/`.** An element id occurs in exactly two places — the `map` key (mirrored in the element's own `id`) and hierarchy `children[].id` — and nowhere else; no action, prop, interaction or payload carries one. A `groupId` occurs in exactly four: `props.groupId` (21), `selectableGroups[].id` (10), `…payload.product.variableId` (5), `…payload.cases[][].predicates[].left.variableId` (4), the last two as the head segment. **And the trap that follows from it:** `tabs-paywall.json` has a group named `tabs` *and* an element whose `type` is the string `tabs`, so a value-keyed rewriter renames `"type": "tabs"` and silently kills the tab bar. The rewriter is path-keyed — it keys on field *names*, never on string values.
- **The oracle, in its corrected form.** A graft output is verify-clean, **or** every remaining `verify-config.py` ERROR corresponds to a defect the plan disclosed in `NEEDS YOU` — the graft introduces no *undisclosed* breakage. The stronger-sounding "always exit 0" form was **measured false**: a `navigate` to a screen the destination lacks is deliberately reported and left alone, because inventing a destination changes routing nothing asked to change. Note why the oracle is not circular: `verify-config.py` predates this feature and errors on precisely the invariants a graft can break.
- **Adopt-by-default for theme clashes**, and why: same id + different value nearly always means both flows call their brand colour `primary`, and a card grafted into another app should look like *that* app. Forking instead grows the destination theme on every graft, which is how a design system rots. Adoption rewrites nothing — the payload keeps its `colorId` and resolves against the destination.
- **A carried typography preset drags its font** — invariant 9's second reference path. `comparison-paywall.json`'s three fonts are reachable *only* through theme presets, zero element-level references. And the converse, which cost a fix round: fonts must be selected at **graft** time from the presets actually carried, because the snippet's font list is a closure computed at **extract** time when the destination is unknown.
- **The structural bug worth remembering: rebind logic that can be bypassed.** `apply_plan`'s `screen` branch once returned before the product-rebind pass, so a cross-app screen graft wrote the source app's product UUIDs while the plan report promised a rebind — and `verify-config.py` exited 0, because bound-but-undeclared is a warning indistinguishable from the correct case. A second instance of the same shape followed: a successful rebind left price-variable heads naming the source products, giving prices that render empty. Both are now one hoisted pass over the payload with a single call site, before any kind branch.
- **Six assertions in this plan shipped unable to fail**, one proven dead only by reverting the code it guarded — a subprocess round trip through JSON cannot observe object identity, so an `is not` check on decoded output tests `json.loads`, not the code. The repo's existing answer is the guarded in-process import (`sys.dont_write_bytecode = True` before the import, as `tests/test-flowkit.py:21-24` does). Every replacement assertion in this work was proven load-bearing by reverting the behaviour and confirming red.
- **Open follow-ups, stated as open**: the behavioural half has **no GREEN round** — no agent has been measured on whether it runs `plan` before `graft`, surfaces an undeclared product as an ask rather than fabricating a `flowProductId`, re-previews after adoption changes a colour, or prints the absolute snippet path; the scenario for that round is in the design spec. And one known one-line gap: `match[0]['id']` in the any-app rebind branch still raises `KeyError` if a catalog row is a dict without an `id` key.
- **Task 12 (2026-08-27, `adapty` 0.8.1) closed the three ASSUMED claims by measurement, against `app_finance`, Grit and NetPrime — full evidence in the design spec's Risks section.** (1) **Cross-app media and font URLs both resolve and draw.** A `flows media upload` CDN URL is not app-scoped: a probe uploaded to `app_finance` loaded (`200 image/png`) and drew visibly inside a different app's flow with zero re-upload. A `_meta.fonts[].url` lifted verbatim from one app's flow rendered in that face inside another app's flow preview — glyphs actually changed shape, not just a resolvable-but-inert reference. Neither needs a rewrite step in a cross-app graft. The font result is preview-only per `flow-schema.md` trap 7: no SDK-integrated device was available to confirm the font *ships*, so a font-carrying graft still needs a named device caveat. (2) **The `fill` shape question is only partially closed.** For a single-layer `color` fill, leaving a snippet's v9 object form unconverted inside a v10 flow validated clean and rendered **MD5-identical** to the destination's own array form — so `snippet.py`'s current no-conversion behaviour is correct for this case, and the design spec's "graft keeps the destination's form" line was aspirational text nothing enforces. But the object/array split is not a clean v9/v10 boundary in the first place — `tests/fixtures/tabs-paywall.json` is a real `schemaVersion: 9` export carrying **15 array-form** fills and it renders (this file, ~line 199) — so what Task 12 actually measured is narrower: a single-layer `color` fill validates and renders identically **in either form**, independent of `schemaVersion`. This does **not** extend to multi-layer, image or gradient fills — the standing multi-layer-fill trap above (tint present in preview, absent on an iOS device) is exactly the shape of failure a single-layer probe cannot rule out, and no device check was run. Guidance updated in `snippets.md`'s Grafting section and the design spec; `snippet.py` itself was not touched (still closed for this task).

## Conventions when editing `paywall-teardown`

- **This skill is vendored, not authored here.** It came from the growth team's claude.ai skill and the library is theirs. Keep repo-specific additions in `SKILL.md` and keep `references/patterns.md` as close to upstream as possible, so their next revision of the library lands as a clean copy rather than a merge. When a pattern's impact range or cross-check changes, it changes upstream first.
- **The impact numbers are priors, and inflating one is the failure mode.** Every range is expected effect calibrated from teardowns, never measured lift for the user's app — which is why the disclaimer is verbatim and non-optional. The single most common defect is assigning a redesign-sized number to a copy tweak; the tier table at the top of the library exists to stop exactly that. Never add a range that is not in the library.
- **Never name a company.** Grounding is category-level only ("near-universal", "common in top fitness apps"). Naming an app critiques a brand Adapty may be selling to.
- **The CTA is conditional on an observable predicate, not on tone.** Include it when the user is looking at something they cannot yet edit (a screenshot, a competitor, a design); omit it when the input is a flow config or a `flows config preview` render, because that user is already inside the builder. Written as a conditional rather than a preference on purpose — a preference gets negotiated away in both directions.
- **`## What you cannot invent` is the safety content, and it is repo-specific.** The upstream skill talks the user out of *reporting* invented stats; here the same skill can feed a generator that *ships* them into a live flow, which is a different blast radius. Its table maps each pattern to what the config can build versus what only the user can supply, and it delegates every mechanic (`old-price`, `_meta.icons`, empty asset maps, variable producers) to `flow-generator` by name rather than restating it. Keep it that way: this skill owns conversion claims, `flow-generator` owns the JSON.
- **The trigger is a predicate, not a vibe.** An earlier draft keyed both call sites on an "abstract brief", which is a judgement the agent makes about the user's tone; it is now keyed on *was a design reference given* — an image, a screen to copy, a spelled-out layout — because that is checkable and because it also catches the ordinary case the word "abstract" misses: a plain "add a paywall screen" where the agent silently picks the whole design. Corollary that must stay attached: **a reference that was given outranks the library**, or the skill starts overwriting the user's own design with its priors.
- **In Design the findings are corrections, not advice.** Pass 2 exists because a screen the agent designed and then merely *reported on* ships every defect it named. The wording — a finding on your own draft is a defect; never hand over a screen with a table of the patterns you skipped — is the whole point of wiring this skill into a generator rather than leaving it a standalone reviewer.
- **The library ranks elements, not compositions, and that produced one screen shape twice.** Read forward, `patterns.md`'s highest-impact entry — the free-vs-paid comparison table — has a `when` clause ("no comparison exists on screen") that is true **by construction** on anything you author, so it fires every time; the rest of the top of the list is plan-card machinery. Measured: two live builds in two unrelated verticals came out as the same comparison-table-over-plan-cards screen, and the proximate cause was a build script copied forward rather than a judgement. Hence `## Choose the archetype first`: seven named compositions, each gated on an **observable prerequisite** (an uploaded asset, a verified intro offer, plans differing only by period), chosen **by the skill and disclosed**, never put to the user as a question — the same reason every other decision in this repo is a named-and-disclosed choice rather than a prompt. Two clauses in it are load-bearing and were added from the same run: a missing prerequisite **rules an archetype out** rather than licensing a placeholder (an image you cannot upload is not an archetype; a trial timeline with no verified offer is a fabricated offer), and **the same archetype twice in a row is a smell** to check against inertia.
- **The two-way link is load-bearing in both directions.** `flow-generator` phase 2 asks who chose the design and invokes this skill when the answer is the agent, putting its asks to the user before any JSON is written; phase 4 runs it over the render and *applies* the Fix-first and High rows, while a correction still costs a screenshot instead of a `config update`. Delete either call site and the pair silently degrades to what it was: a generator with no taste, and a teardown with nothing to tear down.
- **Untested by subagent, and that is recorded rather than hidden.** The Iron Law in `superpowers:writing-skills` wants a baseline round before the content lands; this skill's repo-specific additions have not had one, because the session that added them was instructed not to dispatch agents. The upstream half arrived already in production use. Treat a GREEN round over the design-brief direction and the two `flow-generator` call sites as the open follow-up, and the highest-value scenario is the one this skill is armored for: "add a paywall screen" with no reference attached, where the agent has no real rating, no real outcome data and no hero asset — the round should score whether pass 2 changed the config or merely described it.
