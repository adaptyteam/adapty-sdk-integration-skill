# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Four portable, Claude-style skills for agentic CLIs (Claude Code, GitHub Copilot CLI, OpenAI Codex, Gemini CLI):

- **`adapty-integration`** — guides an agent through integrating the Adapty SDK into a mobile app end-to-end: dashboard setup via the Adapty CLI, SDK install, paywall, store configuration.
- **`ads-manager`** — operates Apple Search Ads through the Adapty CLI's `adapty asa` topic: reading performance, changing bids and budgets, keyword work, launching and pausing campaigns.
- **`flow-generator`** — reads a flow's Flow Builder config (JSON) through the CLI's `flows` topic, transforms it, and writes it back. Touches no app code; touches the CLI for the config itself and for products.
- **`paywall-teardown`** — reads a paywall (a screenshot, a `flows config preview` render, or a flow config) against a pattern library and returns ranked, testable conversion hypotheses with expected-impact ranges. Touches nothing: no CLI, no files, no network. The growth half of the pair whose engineering half is `flow-generator`.

One repo, three distribution channels: a Claude Code plugin (`.claude-plugin/` holds the marketplace + plugin manifests), the skills.sh CLI, and plain directory copy of a `skills/<name>/` directory into a tool's skills folder. Keep every skill directory self-contained and format-portable — nothing in one may assume Claude Code specifically.

All four skills ship inside the single `adapty-skills` plugin, because a plugin exposes every skill under `skills/`. No manifest edit is needed to add one. The plugin name is deliberately broader than any one skill — installing it gives you every skill in the repo, and that is the intended shape. Splitting the skills into separate marketplace entries was considered and rejected; do not reopen it without a reason the plugin name no longer covers.

`marketplace.json` also carries a **deprecated `adapty-sdk-integration` entry** pointing at the same `source: "./"`, so installs made under the old plugin name keep resolving and keep updating. Verified: `plugin details` through either handle reports the same plugin identity and the same skill inventory. Drop that entry only after the docs stop teaching the old handle — never before, or you break the installs it exists to protect.

**Three namespaces, renamed together:** the GitHub repo is `adapty-skills`, the plugin is `adapty-skills`, and the SDK skill is `adapty-integration` (the ads and flow skills keep their names). They are independent namespaces that happen to agree now — a future change to one does not imply the others. Note the repo rename has no alias mechanism the way the plugin does: GitHub redirects git and web traffic from the old name indefinitely, but **`raw.githubusercontent.com` does not follow renames**, so any consumer fetching raw file URLs breaks the moment the rename lands and must be updated in the same wave. The redirect also dies permanently if anything is ever created at `adaptyteam/adapty-sdk-integration-skill` again, so never reuse that name.

## Layout

- `skills/adapty-integration/SKILL.md` — the skill entry point. Phase-by-phase flow: state tracking → setup (docs-fetching rules, session marker, feedback consent) → project analysis → three user questions → dashboard setup through the Adapty CLI → staged, per-platform implementation → closing review → feedback delivery. Platform-agnostic on purpose; per-platform details belong in references.
- `skills/adapty-integration/references/<platform>.md` — one per platform (`ios`, `android`, `flutter`, `react-native`, `unity`, `kmp`, `capacitor`) plus `testing-setup-{ios,android}.md`. Code snippets and the exact docs URLs the agent fetches before writing each piece of code.
- `skills/adapty-integration/references/migration.md` — the cross-platform migration spine: source detection, mapping rules from another purchase system's concepts to Adapty's, and the `ADAPTY_SETUP.md` handoff contract. Injected on every run where `migrationSource` is set, alongside the platform reference; kept lean on purpose, since a headless run can't skip past padding. `references/migration-<source>.md` (currently `migration-revenuecat.md`) adds source-specific mapping and is also cross-platform. Two files are the odd ones out, loaded **on demand only** and never injected by default: `references/migration-architecture.md`, when a call site has no one-to-one Adapty equivalent, and `references/migration-flow-rebuild.md`, when `paywallApproach` is `flow_builder` and the app renders its paywall screen itself — the one migration that retires the app's own UI instead of rewiring it. That file owns the two rules the spine can't state generally: no CLI-created placements on such a run (the flow needs those developer IDs), and the screen's copy, assets, and locales get extracted into the handoff before any code changes, because the user rebuilds it in a visual editor from what the agent wrote down.
- `skills/ads-manager/SKILL.md` — the ads skill's entry point. Ten named workflows (orient, report, launch, harvest keywords, optimization pass, pause/resume, custom product page, diagnose a dead ad, automations, competitor check), a money-safety contract in prohibition + rationalization-table + red-flags form, the shared account surface, the one-question-one-call rule, and the fallback chain. Drives the `adapty asa` topic, added by [adapty-cli#8](https://github.com/adaptyteam/adapty-cli/pull/8) and shipped in `adapty` 0.4.0.
- `skills/ads-manager/references/asa-management.md` and `asa-metrics.md` — the writing half and the reading half. Management owns per-entity create/update flags, the scope-filter matrix, batch caps, idempotency and the catalog/write budgets; metrics owns entity levels, cohort windows, date-window caps, the metric vocabulary and the analytics pool. The split is load-bearing: the two halves share almost no vocabulary, so a "how did last week go" request loads one file and "add these keywords" the other. `SKILL.md` links into both by exact heading string — `## Scope filters`, `## Writes and idempotency`, `## Status`, `## Cohort windows`, `## The analytics pool` — so renaming a heading breaks the entry point silently.
- `skills/flow-generator/SKILL.md` — the flow skill's entry point. Owns the **five-phase workflow** (authenticate → decide new-vs-existing flow and transform → `flows config validate` → `flows config preview` + screenshot + iterate → `flows config update`, read back, hand off the publish), the safety contract (`--expected-updated-at` on every write but the first, never write to a flow the user did not name, prefer a fresh `flows create` for new work, no `flows delete` so never claim to have deleted one), and the verify checklist. The phase ordering is load-bearing: validate and preview both run on a **local file**, so the loop converges before anything is written — one write instead of one per iteration. Four transforms are in scope and a request outside them is named as out of scope, not improvised: add a locale, rewrite copy, add/remove/reorder screens, branching and conditions. Transforming a real config is the default and the safer path, but **authoring is in scope too** and the skill ships `references/flowkit.py` for it. Exactly three things cannot be synthesized: **`flowProductId`** (builder-only; measured not to be a plain UUIDv5 over the obvious inputs), **uploaded assets**, and **real store prices**. The earlier, broader claim — that product UUIDs, icon SVG and the `theme` were also unsynthesizable — was disproved by building several flows from screenshots; do not restore it, because an agent that believes it refuses work it can do.
- `skills/flow-generator/references/flow-schema.md` and `transforms.md` — the shapes half and the risk half. `flow-schema.md` owns the envelope, the browser-export-versus-CLI-config distinction, the element/action/sizing vocabulary (recorded with per-file provenance, and explicitly a floor rather than a closed set), the shape traps, and the invariant table. `transforms.md` owns, per transform, which invariant is at stake, which publish blocker it trips, and what has to be disclosed to the user. The split is load-bearing the same way `ads-manager`'s is — a copy rewrite needs the rich-text rules and nothing about branching; a quiz rewire needs the condition wiring and nothing about locales. `SKILL.md` links into `transforms.md` by exact heading string, so renaming a heading breaks the entry point silently.
- `skills/flow-generator/references/preview.md` — the evidence behind phase 4, split out to keep the entry point loadable: why the URL is unreadable, what a screenshot is and is not evidence of, the **six render blindnesses**, the four disagreeing surfaces, and the failure path (analytics beacons choke on a large fragment → use the file-input script, never a smaller config). `SKILL.md` phase 4 is now the loop alone and links here by heading.
- `skills/flow-generator/references/products.md` — product binding, split out because a locale or copy run never needs any of it. Owns the fact that a flow's `product.id` and the Adapty product UUID from `adapty products list` are the same namespace (verified, not inferred), the read-only lookup chain (`apps list` → `access-levels list` → `products list`/`get`), the `products create` write and its confirmation gate, and the `--period`-versus-price-variable agreement check. It also records the three ways `products create --help` misdescribes required flags (all found by running the command, not by reading it) and the verified fact that a `const` purchase action binds a product with no `product` element and no `_meta` declaration.
- `skills/paywall-teardown/SKILL.md` — the paywall skill's entry point. Owns the **two directions** — audit a paywall someone else will change, or *design*, which is entered on an observable predicate (**no design reference was given**: no reference image, no screen to copy, no layout spec) and runs two passes, the second of which grades and corrects the agent's own render — the three input forms (screenshot / `flows config preview` render / flow config), the internal four-step process, the two output formats, the verbatim disclaimer, the conditional CTA, and the framing rules that keep the numbers honest. Adapted from Adapty's growth-team `paywall-teardown` skill shipped on claude.ai; the additions here are the render/config inputs, the design-brief direction, the `## What you cannot invent` section, and the two-way link with `flow-generator`.
- `skills/paywall-teardown/references/patterns.md` — the pattern library: 15 patterns plus category playbooks, each with when it applies, its cross-check, its impact tier and its category-level grounding. **Kept at that filename deliberately**, matching the upstream skill so a growth-team update to the library copies in as a one-file diff — even though `skills/flow-generator/references/patterns.md` is a different file about layout composites. They never own the same fact: conversion patterns and impact numbers here, JSON skeletons there.
- `tests/` — the fixture corpus for `flow-generator` and its two Python helpers (see the `flow-generator` conventions below). Not a test suite for the skills.
- `scripts/` — the two validation lints and their plain-text allowlists (see below).
- `feedback-endpoint/` — a single Vercel serverless function that receives the end-of-run feedback payload and forwards it to Slack + Airtable. Deployed separately (`npx vercel deploy --prod` from inside that directory); its README documents the env vars and the stable production URL that SKILL.md points at. Has its own tests: `node --test test/endpoint.test.js` from inside that directory.
- `context7.json` — Context7 indexing config.

## Validation lints

**The lints cover `skills/adapty-integration/` only.** Both scripts hardcode that path (`scripts/lint-links.mjs:35`), so nothing under `skills/ads-manager/`, `skills/flow-generator/` or `skills/paywall-teardown/` is checked by them, by CI, or by the daily drift cron — a green run says nothing about those three. Verify their URLs by hand until the lints are widened, which is an open follow-up. (The symbol lint would have nothing to say about `flow-generator` or `paywall-teardown` in any case: neither names an SDK symbol.)

There is no test suite for the skills themselves — the lints are the verification gates for the one they cover. Run them after any edit to that skill's SKILL.md or a reference:

```bash
node scripts/lint-symbols.mjs [platform ...]   # default: all platforms
node scripts/lint-links.mjs
```

Exit codes for both: `0` clean (warnings allowed), `1` findings, `2` infrastructure error (docs unreachable — fix the network, not the skill).

- **Symbol lint** — every Adapty-branded symbol used in a reference's code contexts (`Adapty.x` / `adapty.x` / `AdaptyUI().x` member calls, `Adapty*` type names, in fenced blocks and inline backticks) must exist in that platform's official docs. Ground truth is the `<platform>-llms-full.txt` docs aggregate plus pages the reference links; the docs are verified against SDK sources by the docs team's release process, so docs presence transitively means the symbol exists in the SDK. A reference's platform comes from its filename (`testing-setup-*` files are pinned to their platform in the script). Two plain-text escape hatches, editable without touching code:
  - `scripts/app-side-allowlist.txt` — wrapper names the references deliberately tell the *user* to create. They look Adapty-branded but are not SDK symbols; add the name here when a reference introduces a new suggested wrapper.
  - `scripts/undocumented-sdk-symbols.txt` — real SDK symbols deliberately absent from the docs. Each entry pins a source-of-truth code URL and is verified against the SDK source instead, so a rename still turns the lint red. Format: `<reference>: <symbol> <source-url>`.
- **Link lint** — every https URL in the skill must work the way an agent fetches it: `adapty.io/docs` pages are checked via their `.md` variant with query/hash stripped, `*-llms*.txt` aggregates as-is. A docs 404/410 is a hard failure (the skill literally instructs fetching that URL); external links (stores, consoles, GitHub) failing are warnings only, as are docs pages missing from `llms.txt` (they work but agents can't discover them).

CI (`.github/workflows/skill-lints.yml`) runs both lints on PRs and pushes to `main` (red blocks merge) and on a daily cron that catches drift with no skill commit involved — docs renames, SDK releases. A scheduled failure files one deduped `skill-drift` GitHub issue; repeats become comments on it.

## Conventions when editing the skills

These apply to `adapty-integration`; the `ads-manager` section below adds its own.

- **Docs URLs are load-bearing.** SKILL.md forbids the runtime agent from guessing slugs — it may only open URLs written in the skill or found in a fetched `llms.txt` index. So every docs URL you add must literally exist (the link lint enforces this); never assemble one from a topic and platform name.
- **The session marker matters.** SKILL.md tells the runtime agent to mint a random `sessionToken` and tag every docs fetch with `?ref=skill-<sessionToken>` (a docs-analytics marker, documented in SKILL.md's "Session marker" section). Don't remove, rename, or add a literal example token to that format — hardcoded example tokens get copied verbatim by agents, which corrupts the analytics.
- **Test runs from this repo are not real integrations.** When you run or debug the skill from inside this repo, have it tag docs fetches with `?ref=skill-dev-<sessionToken>` instead (or drop the `ref` on ad-hoc curl spot-checks), so Adapty's docs analytics can tell development traffic from real usage. The lint scripts already strip refs and need no special handling.
- **New wrapper names need the allowlist.** If a reference introduces a new app-side wrapper (service, notifier, context, constant) with an Adapty-ish name, add it to `scripts/app-side-allowlist.txt` in the same change, or the symbol lint turns red.
- **New platform = new reference + docs coverage.** Add `references/<platform>.md` and confirm the docs publish `<platform>-llms-full.txt` — the symbol lint builds its ground-truth corpus from it.
- **New migration source = new reference + spine row.** Add `references/migration-<source>.md`, add a row to the spine's detection table, and add the source to the CLI's picker if the CLI should offer it. No lint edit is needed — the symbol lint prefix-matches `migration*` and derives the platform list.
- **Migration references are linted against the union corpus.** Their Adapty symbols are still verified, so they may name Adapty APIs; they carry mapping and strategy and delegate platform code to `references/<platform>.md`. Dead `revenuecat.com/docs` links are hard lint failures — take RC URLs from `https://www.revenuecat.com/docs/llms.txt`, never assemble one.

## Conventions when editing `ads-manager`

- **Verify against per-command source, never prose and never flag-set composition.** Ground truth for the `asa` surface is each command's own `static flags` declaration in `adaptyteam/adapty-cli`. The CLI's prose docs contradicted that source in four separate places while this skill was written (`--search` coverage, `--page-size` limits, `--period-unit` casing, `product-pages sync` 200 semantics), and composition misleads in its own way — `orgScopeFlags` contains no `--org`, which is exactly where a hallucinated `--org` list filter came from. Read `src/commands/asa/<topic>/<command>.ts`, not the tables.
- **The surface moves.** This skill was authored against adapty-cli#8 while it was open, and that branch gained a commit mid-authoring which silently invalidated facts already verified — `--page-size` limits, the request budgets, the 429 retry behaviour. It merged at `47528602`, the commit the current content is verified against. Pin the commit you verify against in your notes and re-check numbers rather than trusting a previous pass, because the next CLI release will do this again.
- **The safety content is evidence-backed, not authored.** The rationalization table carries exactly two rows, both byte-exact quotes from agents in `docs/superpowers/baselines/2026-08-11-asa-baseline.md`. Never add a row without a real quote from a real run — a fabricated excuse teaches a failure mode nobody exhibited. Red flags are grouped by provenance: those observed in this skill's own baseline, and those adopted from CLI-side reports. Keep the groups separate so a reader can tell which armor rests on measurement.
- **Match the form to the failure.** Two rules had to be rewritten because the form was wrong, not the content. A rule that governs intent ("never pass `--yes` until the user agrees") is satisfiable by an agent that plans to comply while the command on the page already carries the flag — ground it in an observable mechanism instead (`--yes` deletes the preview the CLI would print). And a rule with no compliant use will get an exception invented for it: the same `--yes` prohibition forbade the flag unconditionally in every realistic request, so it became two conditionals keyed to who runs the command.
- **Slots beat reminders.** Required elements live in the command templates as slots an agent cannot fill from memory — `--idempotency-key <key>`, and the deliberately clumsy `--<filter-from-that-list-s-matrix-row>`. That token's length is load-bearing: shortening it back to `--<scope-filter>` makes it fillable by guessing and reopens a closed hole.
- **Changes get pressure-tested, and one clean sample proves nothing.** The scenarios and the twelve-row checklist are in the baseline document. A clean round was twice shown to be luck by re-sampling the identical skill, so a rule is considered closed only after two consecutive clean rounds.
- SKILL.md and the references are agent-facing prose: imperative, unambiguous, no dead weight. Match the existing voice and structure when editing.

## Conventions when editing `flow-generator`

Every rule below exists because it was violated while the skill was built.

- **One owner per fact; link, never restate.** `references/products.md` owns product binding, `references/flow-schema.md` owns shapes and invariants, `references/transforms.md` owns per-transform risk and the five-item disclosure contract, and `SKILL.md` owns workflow, safety, verify and preview. A fact stated in two files will drift, and it did inside a single authoring session: `flowProductId` was described as flow-scoped in one file and assignment-scoped in another, and only one of those is true. When a second file needs a fact, link to the file that owns it.
- **Do not write guidance for a trap the baseline already closed.** Measured against skill-less agents in `docs/superpowers/baselines/2026-08-19-flow-generator-baseline.md`: they preserve rich-text `variable` price nodes (2/2), repair a dangling `navigate` nested in a `conditional`'s `default` branch (2/2), and find all 42 localizable fields (2/2). What actually failed was `status`/`id` on re-upload (0/4) and undisclosed structural decisions — bare-string `content` handling split 2 agents left / 2 converted, with 0/4 disclosing it as a choice. Content that teaches mechanics agents already have is padding, and padding is what a headless run cannot skip past. Guidance earns its place by naming stakes and forcing disclosure, not by walking JSON.
- **`--help` is not the command manifest. Enumerate `dist/commands/`.** `flows config validate` and `flows config preview` exist in the package, are listed in `oclif.manifest.json`, and were **absent from `flows config --help`** on the version checked — which produced a confident, wrong claim that neither command existed. The reliable enumeration is `find "$(npm root -g)/adapty/dist/commands" -name '*.js'` (or the npx cache path), plus reading the command's own `static flags` and `static description`. This is the same rule `ads-manager` already carries, one level deeper: not just "prose lies about flags" but "help output omits whole commands."
- **Check which version you actually invoked.** The 404-on-validate investigation crossed two versions without noticing: `npx adapty@latest` ran **0.6.0** while the inspected npx cache directory held **0.6.1-beta.0**. `validate`/`preview` are in the beta only. Print `--version` in the same command as the thing you are testing, and never read a cached `node_modules` as evidence about a different tag.
- **The `flows` CLI version floor is per command, verified from the published tarballs, and it does not move monotonically.** Read off `npm view adapty@<v> dist.tarball` + `tar -tzf | grep commands/flows` — the only enumeration that neither `--help` (hides commands) nor a global install (usually stale) can lie about. `flows` + `config get/update` from **0.6.0**; `config preview` from 0.6.1-beta.0 and **stable since 0.7.0**; `config validate` in 0.6.1-beta.0, **absent from 0.7.0**, back in 0.8.0-beta.0; `flows media upload` 0.8.0-beta.0 only. Two consequences the earlier "validate and preview are beta-only" note got wrong: **`@beta` is not needed for the normal loop** (stable `latest` covers phases 1-5, preview included), and **a command can leave stable again**, so "a later version has it" is not inferable from an earlier beta. The skill now resolves **`$ADAPTY`** once in phase 1 — `adapty` if `--version` is >= 0.7.0, else `npx --yes adapty@latest` — and every runnable example is written against that variable rather than a bare `adapty`, which is what let three agents conclude the commands did not exist. **`--yes` is load-bearing**: without it npx asks permission to install an uncached package and a headless run has nobody to answer. Facts about behaviour, each established by running the commands: `config get` returns an **envelope** (`{config, remote_configs, status, updated_at}`); `--expected-updated-at` wants the **epoch integer** from `config get` and rejects the ISO timestamp `flows create` prints; `validate` is advisory, exits **1 for both "not publishable" and "API error"**, and its endpoint **404s** on 0.8.0-beta.0, so the `--json` `valid`-versus-`error` distinction is load-bearing; `preview` is **fully local** (no `--app`, no flow id, no auth) and accepts an envelope or a bare config; `flows media upload` also 404s, so uploaded assets stay unreachable; and there is **no publish and no delete**, so both stay dashboard actions. **Never invent a command name or a flag** — if a command is absent, the skill says so and falls back.
- **`flows media upload` is documented as absent on purpose, and that is a release decision, not a measurement.** The command ships in `adapty` 0.8.0-beta.0 and its endpoint is live **on dev only** ([ADP-7610](https://adaptyio.atlassian.net/browse/ADP-7610)), so this branch ships the skill with the commands that are actually live in production and the runtime agent is told **not to call it and not to offer it** — an image the agent does not have stays an empty values map (trap 5) and the user uploads it in the Flow Builder. Adding the upload path is a **separate branch** once the endpoint ships in production; when it does, the change is the CLI-surface line, the trap-5 escape hatch, and `paywall-teardown`'s hero-archetype prerequisite, which is currently ruled out precisely because no asset can be supplied.
- **Overwriting an existing config requires an explicit yes; a brand-new flow does not.** The gate is keyed to an observable fact — does `config get` return a config — rather than to the agent's confidence, because a clean `validate`, a good screenshot and a user who liked the design are all upstream of the question and none is an approval. The ask is a fixed block naming the flow, its id, its status, the change summary and the restore path, because an approval given without those is not informed. Two supports underneath it: a `published` or `dirty` target makes **building into a fresh `flows create` the recommended route**, and the phase-2 backup is what makes recovery real — **measured**: an element deleted, written, then restored from `flow.backup.json` came back **byte-identical**, with the one wrinkle that the agent's own write invalidates the `updated_at` it was holding, so the restore has to re-read it first.
 The gate also has to *show* the change, which is three things and not one: a before/after render pair per touched screen (`preview` eats the backup envelope as-is), the local `preview` command handed to the user so they can open and **tap** it themselves — the only pre-approval way to catch a selected-state defect, which is precisely the class that shipped from this skill — and the structural summary, because **identical screenshots do not mean an identical config**: measured, deleting an entire `bottom-sheet` element gave a byte-identical render, since the sheet was hidden in the state that draws.
- **The dev environment is where `validate` and `media upload` actually work, and testing them means two env vars — one set, one deliberately unset.** `ADAPTY_API_URL=https://app.dev.adpinfra.dev/api/v1/developer` points the CLI at dev, which is why those two endpoints 404 against production and why the skill treats them as absent. **`ADAPTY_APP_URL` must stay unset**: the CLI reads it as an *override*, so unsetting it lets login follow the host the dev API issued while previews fall back to the prod render page — and pointing it at dev breaks previews outright, because the dev UI is behind SSO and a headless capture screenshots a GitLab login page. Also per-environment: **auth tokens and app UUIDs both differ**, so a prod token and a prod app id are equally useless on dev. Source: the internal `adapty-flow-config` testing draft, which is where the follow-up media branch should start.
- **Findings adopted from the internal `adapty-flow-config` draft, each re-verified here before it landed.** Its `update` returns the **same envelope as `get`** (checked key for key, plus `config`, `updated_at` and `status`), so phase 5 redirects the write over the working file instead of re-fetching — and a write that changes nothing **does not bump `updated_at`** (measured once). Its bug list explains the large-flow preview failure as *third-party analytics beacons* putting a 113K `location.href` into their own query strings and getting a 414, not an Adapty size limit, which is why phase 4's fallback is now the file-input script rather than the dashboard. Two of its claims did **not** survive re-testing and are recorded as such rather than copied: the renderer dropping every `position: fixed` element reproduced on a v9 flow and **not** on a v10 one in either docked form, and `flows media upload` returning a numeric `id` where a config needs a string is a note for the media branch, not for this one.

- **`SKILL.md` is loaded on every run, so its size is a latency cost, and it is capped by moving evidence out rather than by deleting it.** Measured: 7,219 words → 4,579 (−37%) by moving phase 4's war stories to `references/preview.md`, the per-version CLI archaeology into this file (which already owned it), and by cutting the dead `validate` call from phase 3 — it is absent from `latest` and 404s where it exists, so the usual run has one check there, not two. The rule that keeps it that way: **SKILL.md holds decisions, commands and output shapes; references hold the measurements that justify them.** A caveat only earns a place in the entry point if an agent must act on it *at that step*.
- **`## What you print` is the user-facing half of that.** The two fixed blocks (the approval ask and the closing callout) are the only fixed output; everything else is one line or omitted, and **each thing is said once**. It is written as a positive recipe rather than a list of prohibitions because that is the form that holds for output-shaping (see `superpowers:writing-skills` → Match the Form to the Failure); the failure it targets is a run that ends in a wall of narration the user has to read past to find what they must do.

- **The support channel (#adp-builder-cs-ps, mined 2026-08-22 back to its 2026-05-18 creation by three subagents) is a fourth evidence source, tiered below our own measurements.** ~41 findings were triaged; team-diagnosed mechanisms with named Jira tickets were adopted, UI-only and analytics-only items dropped, and every adoption sits in its owner file: transformer sizing traps 15-17, `purchase` termination, groupId rules and the small-device facts in `flow-schema.md`; the Android offer-ordering trap (matched by `vendorProductId`+`basePlanId`, `offerId` ignored, order = creation order, republish reorders) in `products.md`; carousel fixed-geometry recipe, layout discipline, toggle re-assert and the countdown delay primitive in `patterns.md`; the l10n tooling gap (ADP-7487) in `transforms.md`; systemic two-way preview/device mismatch plus stub prices in `preview.md`; stale-sizing and groupId checks in `verify-fixture.py` (calibrated against `vpn-timer-draft.json`, a real export carrying 16 benign stale values — hence warning-not-error, error only past screen height). Three channel findings independently **confirmed** our own measurements: the emoji-hug clipping (their transformer measures a 24pt emoji as 17px; same fixed-box fix), conditional text being locale-scoped data, and "compare against strings". One **contradicted** a pattern we ship — ADP-6828, `fixed`+`left/right`+`width:auto` collapsing on device — and is recorded as historical with our 2026-08-22 device screenshot as evidence it now renders, sandwich workaround kept as the fallback. ## Conventions when editing `paywall-teardown`

- **This skill is vendored, not authored here.** It came from the growth team's claude.ai skill and the library is theirs. Keep repo-specific additions in `SKILL.md` and keep `references/patterns.md` as close to upstream as possible, so their next revision of the library lands as a clean copy rather than a merge. When a pattern's impact range or cross-check changes, it changes upstream first.
- **The impact numbers are priors, and inflating one is the failure mode.** Every range is expected effect calibrated from teardowns, never measured lift for the user's app — which is why the disclaimer is verbatim and non-optional. The single most common defect is assigning a redesign-sized number to a copy tweak; the tier table at the top of the library exists to stop exactly that. Never add a range that is not in the library.
- **Never name a company.** Grounding is category-level only ("near-universal", "common in top fitness apps"). Naming an app critiques a brand Adapty may be selling to.
- **The CTA is conditional on an observable predicate, not on tone.** Include it when the user is looking at something they cannot yet edit (a screenshot, a competitor, a design); omit it when the input is a flow config or a `flows config preview` render, because that user is already inside the builder. Written as a conditional rather than a preference on purpose — a preference gets negotiated away in both directions.
- **`## What you cannot invent` is the safety content, and it is repo-specific.** The upstream skill talks the user out of *reporting* invented stats; here the same skill can feed a generator that *ships* them into a live flow, which is a different blast radius. Its table maps each pattern to what the config can build versus what only the user can supply, and it delegates every mechanic (`old-price`, `_meta.icons`, empty asset maps, variable producers) to `flow-generator` by name rather than restating it. Keep it that way: this skill owns conversion claims, `flow-generator` owns the JSON.
- **The trigger is a predicate, not a vibe.** An earlier draft keyed both call sites on an "abstract brief", which is a judgement the agent makes about the user's tone; it is now keyed on *was a design reference given* — an image, a screen to copy, a spelled-out layout — because that is checkable and because it also catches the ordinary case the word "abstract" misses: a plain "add a paywall screen" where the agent silently picks the whole design. Corollary that must stay attached: **a reference that was given outranks the library**, or the skill starts overwriting the user's own design with its priors.
- **In Design the findings are corrections, not advice.** Pass 2 exists because a screen the agent designed and then merely *reported on* ships every defect it named. The wording — a finding on your own draft is a defect; never hand over a screen with a table of the patterns you skipped — is the whole point of wiring this skill into a generator rather than leaving it a standalone reviewer.
- **The library ranks elements, not compositions, and that produced one screen shape twice.** Read forward, `patterns.md`'s highest-impact entry — the free-vs-paid comparison table — has a `when` clause ("no comparison exists on screen") that is true **by construction** on anything you author, so it fires every time; the rest of the top of the list is plan-card machinery. Measured: two live builds in two unrelated verticals came out as the same comparison-table-over-plan-cards screen, and the proximate cause was a build script copied forward rather than a judgement. Hence `## Choose the archetype first`: seven named compositions, each gated on an **observable prerequisite** (an uploaded asset, a verified intro offer, plans differing only by period), chosen **by the skill and disclosed**, never put to the user as a question — the same reason every other decision in this repo is a named-and-disclosed choice rather than a prompt. Two clauses in it are load-bearing and were added from the same run: a missing prerequisite **rules an archetype out** rather than licensing a placeholder (an image you cannot upload is not an archetype; a trial timeline with no verified offer is a fabricated offer), and **the same archetype twice in a row is a smell** to check against inertia.
- **The two-way link is load-bearing in both directions.** `flow-generator` phase 2 asks who chose the design and invokes this skill when the answer is the agent, putting its asks to the user before any JSON is written; phase 4 runs it over the render and *applies* the Fix-first and High rows, while a correction still costs a screenshot instead of a `config update`. Delete either call site and the pair silently degrades to what it was: a generator with no taste, and a teardown with nothing to tear down.
